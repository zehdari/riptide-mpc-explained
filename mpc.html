Chapter 4

The optimal control problem

Every 50 ms the controller asks one question: which thrust, for each of the next 30 intervals, keeps Talos closest to its reference without wasting effort? This chapter writes that question down exactly.

The problem, in one line

With N = 30 stages of \Delta t = 50 ms (a 1.5 s horizon), the decision is the sequence of thruster commands U = (u_0, \dots, u_{N-1}), eight numbers per stage. riptide_mpc solves

\begin{aligned} \min_{U}\quad & \sum_{k=1}^{N} w_k\, \big\| y_k(x_k) \big\|^2_{Q} \;+\; \sum_{k=0}^{N-1} r\,\big\| u_k - u^{\text{ff}}_k \big\|^2 \\ & \;+\; \sum_{k=0}^{N-1} r_\Delta \big\| (u_k - u^{\text{ff}}_k) - (u_{k-1} - u^{\text{ff}}_{k-1}) \big\|^2 \\[4pt] \text{s.t.}\quad & x_0 = \Phi_{\text{delay}}(\hat x), \quad x_{k+1} = F(x_k, u_k), \quad |u_k| \le 24\ \text{N} \end{aligned}

Each piece has a job:

  • F is one 50 ms stage of the Fossen model with the thruster lag, the step from Chapter 1 run 25 times with u_k held. It is nonlinear, which is why Chapter 5 exists.
  • y_k is a 12-vector of tracking errors against the reference at the end of stage k, weighted by the diagonal Q; w_k = 1 except the terminal stage, w_N = 5.
  • Effort and smoothness are measured from u^{\text{ff}}_k, the thrust that inverse dynamics says the reference needs. Following the reference is free; only deviating from it costs.
  • x_0 is not the measured state but where the vehicle will be when this command takes effect, 30 ms from now.

The horizon as a graph

It helps to draw the problem as a factor graph: circles are variables, squares are terms of the cost. States form a chain, each linked to the previous state and one command by the dynamics; each state carries its own tracking cost; consecutive commands share a smoothness term.

That second picture is the whole design choice of Chapter 5 in miniature. Because x_0 is fixed and every later state is a function of the commands, the states can be eliminated (condensing), leaving an unconstrained-dynamics problem in the 240 commands alone. The price is that the graph becomes dense: command u_0 is now connected to all 30 costs, and the Hessian couples every pair of stages.

The state and the decisions

The prediction state is the 13-number body state of Chapter 1 plus the eight realized thruster forces:

\tilde x = (p,\ q,\ v,\ \omega,\ f) \in \R^{3} \times S^3 \times \R^3 \times \R^3 \times \R^8

The forces are states because the thrusters lag (Chapter 2): a command sets the target that f moves toward. Perturbations of \tilde x live on its tangent space, three numbers for attitude instead of four, so the linearized state has 12 + 8 = 20 dimensions. The commands u_k \in [-24, 24]^8 are the only decision variables. On Talos that is 30 × 8 = 240 numbers.

What "close to the reference" means

The error vector compares the predicted state at the end of each stage with the reference profile sampled at the same instant (Chapter 3). For position-mode control:

y_k = \begin{bmatrix} p_b - p_{\text{ref}} \\ \operatorname{Log}\!\big(q_{\text{ref}}^{-1} \otimes q\big) \\ v_b - R(q)^\top v_{\text{ref}} \\ \omega - R(q)^\top \omega_{\text{ref}} \end{bmatrix} \in \R^{12}

Position and velocity are those of base_link, not the COM (p_b = p + R(q) r_{bl}, v_b = v + \omega \times r_{bl}), because that is the point the setpoints are about. The attitude error is the rotation vector of the relative rotation, which is a proper distance on rotations: small, smooth, and the same in every direction, with none of the wrap-around or gimbal problems of differencing Euler angles. Velocities are compared in the body frame.

The weights depend on the mode each half of the command is in:

Why 3000 on roll and pitch? The forward thrusters sit above and below the COM, so any surge thrust is also a pitch moment, and a cheap way to "move forward" in a cost function is to tip the nose. A heavy tilt weight forbids that trade, and the restoring torque from buoyancy (Chapter 1) means holding level costs little thrust. The same numbers are in config/mpc.yaml and can be changed live.

Effort about the feedforward

A plain effort term r\|u_k\|^2 has a flaw: it pays the controller to use less thrust than the reference needs. Holding depth against 1.6 N of buoyancy, or cruising against drag, would then always come with a steady lag, the point where the tracking cost of lagging balances the effort cost of thrust. riptide_mpc penalizes the deviation from a feedforward instead, computed by running the model backwards along the reference:

\boldsymbol\tau^{\text{ff}}_k = \mathbf M\big(\dot{\boldsymbol\nu}_{\text{ref}} - \dot{\boldsymbol\nu}\,\big|_{x_{\text{ref}},\ \tau = 0}\big), \qquad u^{\text{ff}}_k = \operatorname{clip}\big(\mathbf T^{+}\boldsymbol\tau^{\text{ff}}_k\big)

The second term is the model's own acceleration at the reference state with no thrust (drag, Coriolis, buoyancy, and the learned disturbance), so \boldsymbol\tau^{\text{ff}} is exactly the wrench that makes the reference's acceleration happen there. The reference's body acceleration comes from its world acceleration, \dot v = R^\top a - \omega \times v, moved from base_link to the COM. Each stage's feedforward is sampled a thruster rise time (80 ms) after the stage midpoint, so the command leads the lagging thrust.

The smoothness term works on the same deviations: r_\Delta\|(u_k - u^{\text{ff}}_k) - (u_{k-1} - u^{\text{ff}}_{k-1})\|^2, with u_{-1} the deviation actually sent last tick. Following a smooth, jerk-limited feedforward is free; jumping away from it is not.

From the pool

The smoothness weight came from a sweep on 2026-10-03. At 0.005 Talos wobbled in hover (0.6–0.9° RMS pitch, about 4°/s); at 0.02 and 0.05 it held pitch to 0.07–0.09° with less total thrust. The controller ships with 0.05.

Planning through the delay

A command computed now starts acting 30 ms from now. Everything sent before it is already queued in the thrusters, and the controller knows exactly what: it keeps a replica of the thruster dynamics, fed every command it publishes. So before planning, it rolls the measured state forward through the delay with those in-flight commands:

// mpc.cpp, MpcController::compute
Point x0{measured, actuator_.forces()};
if (settings_.compensate_delay) {
    ThrusterDynamics actuator = actuator_;            // copy of the replica, queue included
    for (int i = 0; i < steps; ++i)
        model_.step(x0.x, actuator, delay / steps);   // Fossen model, in-flight thrust
    x0.f = actuator.forces();
}

Stage 0 of the plan then starts at the instant the new command lands. The reference profile is kept on the same clock (it describes where the vehicle should be at now + 30 ms), so a new setpoint starts moving exactly when thrust can first respond to it.

Receding horizon

Of the 240 numbers it solves for, the controller uses eight. The rest are a plan it throws away 50 ms later, except as next tick's starting guess (Chapter 5). In the plot below each thin green curve is the position the controller predicted at one tick, 1.5 s ahead.

Modes

Autonomy commands the linear and angular halves separately (riptide_msgs2/ControllerCommand): POSITION (track a pose via the profile or a path), VELOCITY (track a body- or world-frame velocity, acceleration-limited), FEEDFORWARD (a raw body wrench, allocated directly, no MPC), or DISABLED. The mode only changes which errors carry weight and how the reference is generated; the optimization is the same.

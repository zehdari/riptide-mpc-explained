Chapter 8

Build your own

Everything in the previous chapters, as a recipe for your own vehicle: the order to build it in, a whole control tick in forty lines, how to identify the model in a pool, and what the pool taught us.

The recipe

The order matters. Each step gives the next one something it can trust.

  1. Write the model once, and share it. Implement the Fossen equation (Chapter 1) as a plain function of state and thrust, with an RK4 step. Use the same code in your simulator and your controller, and test that they agree. Every later bug is easier to find when the controller's model is known to be the plant in sim.
  2. Get thrust right first. Get a force-against-RPM curve for each direction: the manufacturer's data if it's good (Talos uses Blue Robotics' published T200 curves), or a load-cell test of your own. Take positions and axes from CAD, build the thruster matrix, and model the delay and lag (Chapter 2). Trust these numbers: identification will attribute everything else to the hydrodynamics.
  3. Weigh it wet. Mass and COM from a scale, in water if you can. Inertia from CAD is fine.
  4. Identify the rest in the pool (below): buoyancy and COB, drag, added mass. Start conservative; a model that is a little wrong is what the disturbance estimate is for.
  5. Make a reference generator before tuning anything: a jerk-limited profile with limits well inside what the thrusters can do (Chapter 3). Add a path planner when autonomy needs to string moves together.
  6. Write down the optimal control problem (Chapter 4): errors on the manifold, diagonal weights with heavy roll and pitch, effort and smoothness about an inverse-dynamics feedforward, box bounds on thrust.
  7. Solve it the simple way (Chapter 5): single shooting, finite-difference Jacobians on the manifold, condense, projected Newton, one iteration per tick, warm-started by shifting. Measure the solve time on the real computer before you go further.
  8. Plan through the delay with a replica of the thrusters fed every command you publish, and keep the reference on the same clock.
  9. Close the loop with your own estimator (Chapter 6): the same model, fast sensors applied raw, slow references blended, and a learned disturbance wrench fed into the prediction.
  10. Add the safety rails: a reference governor, re-seeding when the vehicle falls far behind, zero thrust and a cleared warm start when killed or when odometry goes stale, a settle signal for autonomy.
  11. Test in simulation, then in the pool, changing one thing at a time, and log the predicted horizon, the reference, the disturbance and the solve time every tick.

A whole tick in forty lines

Python-flavoured pseudocode of MpcController::compute, without the path and identification branches. F is one 50 ms stage of the model; plus and minus are \boxplus and \boxminus.

def tick(x_meas, goal):
    # 1. where the vehicle will be when this command lands
    x0 = rollout(x_meas, thruster_replica.copy(), duration=DELAY)
    # 2. reference: profile samples at the end of each stage, and feedforward thrust
    refs = [profile.peek(k * DT) for k in range(1, N + 1)]
    refs_lead = [profile.peek(k * DT + DT / 2 + RISE) for k in range(N)]
    u_ff = [allocate(M @ (ref.accel - accel_unforced(ref.state))) for ref in refs_lead]
    # 3. warm start: last plan shifted one stage
    U = clip(shift(U_last) if U_last else u_ff, -24, 24)
    # 4. roll out and linearize
    xs = [x0]
    for k in range(N):
        xs.append(F(xs[k], U[k], fine=True))
    H = zeros(N*8, N*8); g = zeros(N*8); P = zeros(20, N*8)
    for k in range(N):
        base = F(xs[k], U[k], fine=False)
        A = column_stack([minus(F(plus(xs[k], eps*e_i), U[k]), base) / eps for e_i in I20])
        B = column_stack([minus(F(xs[k], U[k] + eps*e_j), base) / eps for e_j in I8])
        P = A @ P; P[:, 8*k:8*k+8] += B                 # sensitivity of x_{k+1} to all U
        y = error(xs[k+1], refs[k])                     # 12-vector
        C = jacobian(lambda d: error(plus(xs[k+1], d), refs[k]))
        W = Q * (TERMINAL if k == N-1 else 1)
        Mk = C @ P
        H += Mk.T @ diag(W) @ Mk
        g += Mk.T @ (W * y)
    # 5. effort and smoothness about the feedforward
    D = U - u_ff
    H += R * I + R_RATE * DtD;  g += R * D + R_RATE * DtD @ D   # first stage vs last sent
    # 6. box QP for the step, then apply
    dU = projected_newton(H, g, lo=-24 - U, hi=24 - U, x0=zeros)
    U = clip(U + dU, -24, 24)
    U_last = U
    u = limit_total(U[0], 73)                           # power budget, keeps direction
    thruster_replica.command(u)
    return u

Everything else in riptide_mpc is refinement of these lines: the governor around step 2, mode-dependent weights in Q, thrusters pinned for identification, numerics. The JavaScript port that runs this site is about 1,800 lines including the model, the profile, the path planner and the solver; it is a good second reference next to the C++.

Identifying the model in a pool

pool_identify (identification.cpp, pool_identify_node.cpp) flies a scripted session with the MPC in position mode, so the vehicle is always under control, and fits the terms that cannot be measured on land. Because thrust is trusted, the realized thrust wrench is known from the commands; whatever the vehicle does beyond that is attributed to the hydrodynamics.

  • Statics from holds at several attitudes (level and tilted 25°). At a still hold, thrust balances the restoring wrench: \tau_{\text{hold}} = -(B - W)\,\hat z in force and \hat z \times (B\, r_{\text{cob}}) in torque, linear in net buoyancy and in B r_{\text{cob}}. Tilting makes the vertical COB offset observable.
  • Drag from steady runs along each axis at several speeds (0.2 to 0.7 m/s, 0.3 to 0.9 rad/s in yaw): \tau - \tau_{\text{hold}} = D_l v + D_q |v| v, a linear least-squares fit per axis.
  • Added mass from the acceleration and braking phases of the same runs: \int (\tau + g - D v)\,dt = \mathbf M\, \Delta v over each window, which avoids differentiating noisy velocity.
  • Optional blocks: each thruster ramped while the other seven hold the vehicle, and null-space patterns while holding, to fit per-thruster gains; and releases, all thrusters off from level and tilted holds, so the vehicle floats up and rights itself with no thruster in the loop, for heave and roll/pitch inertia and damping.

Fits are checked before they are accepted: added mass above 5× the rigid mass (3× for rotations) is rejected, and the inertia fit is repeated with the thrust delayed by up to 0.6 s; if a delay over 0.25 s explains the data better, the "inertia" is really actuation lag and is rejected. Sessions can iterate: fly, fit, load the fit into the MPC, fly again, until two fits agree.

Lessons from the pool

Everything below happened to Talos
  • Never identify statics with a tether on. The tether's pull was fitted as buoyancy and COB, and showed up untethered as a constant learned disturbance of +2.7 N·m in pitch.
  • Don't let a sanity limit throw away the real answer. Every session measured Talos's surge inertia at 115–158 kg, but a fixed 3× rigid-mass limit rejected the fits as "probably ESC lag", so the model flew with 66 kg and the feedforward pushed half as hard as needed. A lag check (re-fit with the thrust delayed 0–0.6 s) showed no delay explains the data; the mass is real. Limits are now per axis, with that check instead of a guess.
  • Per-thruster scales can hurt. Fitted from holds only, they made small surge corrections pitch the robot; the team set them back to 1.0 until better data came in.
  • Acceleration limits shape everything. At 0.5 m/s² a 3 cm step took ±23 N bursts and pitched Talos 8°. 0.1 m/s² with 0.3 m/s³ jerk is gentle and still fast enough.
  • Tune smoothness, not just tracking. Raising the thrust-rate weight from 0.005 to 0.05 cut hover pitch wobble from 0.6–0.9° RMS to under 0.1°, with less thrust.
  • Measure your filter's lag. Talos's EKF velocity trailed the DVL by 0.2–0.35 s and its roll and pitch rates trailed the IMU by 0.45 s, from a gyro covariance 10,000× too large and too little velocity process noise. Both are fixable, but building the control state from raw sensors with the model makes the controller independent of them.
  • Check what the firmware actually does. An ESC CAN decoding bug needed a 140 rpm offset for a while; a model identified with the offset in place had to be re-identified once the firmware was fixed.
  • Know your thrust budget. Drag at 0.6 m/s is about 90 N against a 73 N budget, so the cruise speed is a wish; the governor makes it safe.

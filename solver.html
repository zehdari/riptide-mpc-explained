Chapter 6

Solving it every 50 ms

The problem of Chapter 5 is nonlinear and has 240 unknowns. riptide_mpc solves it with one Gauss–Newton step per tick, on a QP small enough to factor densely, warm-started from the last plan. In C++ that takes about 11 ms.

Here is the whole of MpcController::compute after the reference is built, in order. Each step gets a section below.

  1. Warm start: shift last tick's 30 commands one stage earlier.
  2. Roll out: integrate the Fossen model through all 30 stages with those commands (2 ms steps).
  3. Linearize: at each stage, finite-difference the stage map on the state manifold to get A_k, B_k, and the error Jacobian C_k.
  4. Condense: chain them into the sensitivity of every predicted state to every command, and build a dense QP in the 240 command changes.
  5. Solve: projected Newton on the box-constrained QP.
  6. Apply: update the commands, publish the first eight.

Perturbing a quaternion

Linearizing means asking how the outcome changes when the state changes a little. For position and velocity, "a little" is just adding a small vector. For attitude it is not: a unit quaternion has four numbers but three degrees of freedom, and adding to it leaves the unit sphere. riptide_mpc perturbs on the manifold instead, with two operators:

x \boxplus \delta = \big(p + \delta_p,\ \ q \otimes \operatorname{Exp}(\delta_\theta),\ \ v + \delta_v,\ \ \omega + \delta_\omega,\ \ f + \delta_f\big)
a \boxminus b = \big(p_a - p_b,\ \ \operatorname{Log}(q_b^{-1} \otimes q_a),\ \ v_a - v_b,\ \ \omega_a - \omega_b,\ \ f_a - f_b\big)

\operatorname{Exp} turns a rotation vector into a quaternion and \operatorname{Log} does the reverse; the perturbation \delta_\theta is a small rotation in the body frame. With these, the state's tangent space has 3 + 3 + 3 + 3 + 8 = 20 dimensions, every perturbation is a valid state, and the linear algebra below never has to know about quaternions.

Jacobians by finite differences

Let F(x, u) be one 50 ms stage. Around the nominal rollout (\bar x_k, \bar u_k), the linear model is

F(\bar x_k \boxplus \delta x,\ \bar u_k + \delta u) \boxminus F(\bar x_k, \bar u_k) \;\approx\; A_k\, \delta x + B_k\, \delta u

Ak is 20 × 20 (state to state), Bk is 20 × 8 (commands to state).

riptide_mpc gets A_k and B_k column by column: perturb one coordinate by \varepsilon = 10^{-6}, run the stage, take the difference. That is 20 + 8 = 28 extra stage simulations per stage, 840 per tick. They use a coarse model (two 25 ms steps per stage, no deadband or saturation in the thruster target, so derivatives are smooth), which makes them cheap. The nominal rollout and the published prediction use the fine 2 ms step.

Finite differences are crude next to automatic differentiation, but they have a decisive advantage here: the Jacobian is of exactly the code that runs, including the thruster lag, the submergence factors, the learned disturbance and the RK4 scheme, with no second implementation to keep in sync.

The error vector y_k of Chapter 5 is linearized the same way, giving C_k = \partial y_k / \partial x \in \R^{12\times 20} at the end of each stage.

Condensing: from a chain to a dense QP

Stack all command changes into \delta U \in \R^{240}. The change in predicted state at the end of stage k is linear in them, \delta x_{k+1} = P_{k+1}\, \delta U, with the sensitivity matrices built by one forward pass:

P_0 = 0, \qquad P_{k+1} = A_k P_k + \begin{bmatrix} 0 & \cdots & 0 & \underbrace{B_k}_{\text{columns of } u_k} & 0 & \cdots & 0 \end{bmatrix}

By causality P_{k+1} is zero in the columns of every command after u_k, and the code only ever multiplies its nonzero left part. Linearizing every error, y_k(U + \delta U) \approx y_k + C_k P_k \delta U = y_k + M_k \delta U, turns the tracking cost into a quadratic in \delta U. This is Gauss–Newton: second derivatives of the dynamics are dropped, so the Hessian is a sum of squares, always positive semidefinite, and cheap.

\begin{aligned} H &= \textstyle\sum_{k} w_k M_k^\top Q M_k + r I + r_\Delta D^\top D \\ g &= \textstyle\sum_{k} w_k M_k^\top Q\, y_k + r (U - U^{\text{ff}}) + r_\Delta D^\top D\, (U - U^{\text{ff}}) \end{aligned}

where D takes differences between consecutive stages (the smoothness term, tridiagonal in blocks). The QP for the step is

\min_{\delta U}\ \tfrac12\, \delta U^\top H\, \delta U + g^\top \delta U \qquad \text{s.t.}\qquad -24 - U \le \delta U \le 24 - U

Why condense instead of keeping the states as variables (a sparse QP with 30 × 20 more unknowns)? For a horizon of 30 and only eight inputs, the dense problem is small: a 240 × 240 Cholesky factorization is about 4.6 million multiply-adds, a fraction of a millisecond. Sparse solvers win when horizons are long or inputs many; here, dense and simple wins, and needs no external solver library.

Box constraints: projected Newton

The only constraints left are bounds on each variable. box_qp.cpp uses Bertsekas's projected Newton method (1982), which exploits that structure:

  1. Compute the gradient Hx + g. A variable is bound if it sits on a limit and the gradient pushes it further out; the rest are free.
  2. If the free gradient is below 10^{-8}, stop: that is the optimality condition for a box QP.
  3. Solve the Newton system on the free variables only, H_{ff}\, d_f = -\nabla_f, with a Cholesky factorization.
  4. Step x \leftarrow \Pi(x + \alpha d), projecting back onto the box, halving \alpha until the projected Armijo condition holds.

When no bound is active, step 3 is the exact minimizer and the solver stops after one iteration. When thrusters saturate it typically needs two to four.

One step per tick: real-time iteration

A full nonlinear solve would repeat roll-out, linearize, solve until the plan stops changing. riptide_mpc does it once (sqp_iterations: 1), then publishes. This is the real-time iteration scheme of Diehl, Bock and Schlöder (2005), and it works because consecutive problems are nearly the same: the last plan, shifted one stage, is already close to optimal for the new one, so a single Newton step from it is close to converged. Each tick refines the plan while the plan itself moves forward in time; the optimization and the system converge together.

The warm start is a shift:

// mpc.cpp: shift the previous solution by one interval (the last stage repeats)
warm_.head(nU - nu_) = warm_.tail(nU - nu_).eval();
VectorXd U = warm_.cwiseMax(lb_).cwiseMin(ub_);

and on the very first tick, or after a reset, the plan starts from the feedforward U^{\text{ff}}, which is already a good guess because it is the thrust that would track the reference exactly if the model were linear.

Each model step is four evaluations of the Fossen derivative, a few thousand floating-point operations; a tick is a few tens of millions. That is about 11 ms (median) in C++ with Eigen on a desktop CPU, and the browser port manages 20–50 ms in JavaScript. The node publishes every solve time on controller/mpc/solve_time_ms and warns if one takes longer than the 50 ms control period.

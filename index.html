riptide_mpc, chapter by chapter

The green line ahead of Talos is the controller's prediction. Every 50 ms it picks thrust for all eight thrusters over the next 1.5 seconds, sends the first 50 ms of it, and starts over. Everything here runs the same algorithm as the C++ on the robot.

Talos is the team's competition AUV: a 34 kg frame with eight thrusters, a DVL, an IMU, a fibre-optic gyro and a depth sensor. Its controller lives in riptide_control/riptide_mpc. This site explains that controller completely: the physics it predicts with, how it decides where the robot should be, how it turns that into an optimization it can solve in a few milliseconds, and how it copes with a model that is never quite right.

If you are building an MPC for your own vehicle, the last chapter is a recipe. The chapters before it are the reasons behind each step.

The loop, one tick at a time

Each piece of the controller is a box below. Hover or tap one to see what it does and where it lives in the code. The dots show data moving through one 50 ms control tick.

In words, a tick goes like this:

  1. Estimate. The state estimator has been propagating the same Fossen model between sensor messages, correcting with the gyros, DVL and depth sensor. It hands the MPC a 13-number state: position, attitude quaternion, body velocity and body rates.
  2. Look ahead through the delay. Thrust takes 30 ms to start responding, and commands already sent are still in flight. The MPC rolls those known commands forward so it plans from where Talos will be when the new command lands.
  3. Move the reference. Setpoints are never chased directly. A jerk-limited profile, or a path planned as one smooth curve, moves the reference toward the goal at speeds the vehicle can actually follow.
  4. Predict and linearize. With last tick's plan shifted one step as a first guess, the model is rolled out 30 stages of 50 ms. Each stage is linearized by finite differences.
  5. Solve a QP. The linearized problem is a quadratic program in 240 numbers (30 stages × 8 thrusters) with box bounds of ±24 N. A projected Newton method solves it, usually in one or two iterations.
  6. Send the first 50 ms. Only the first stage's thrust is published, scaled to the 73 N power budget if needed, and converted to propeller RPM. Next tick, it all happens again.

Why a nonlinear MPC

An AUV has a few properties that make a predictive controller worth its cost. The thrusters are coupled: no single thruster moves Talos along one axis, so every motion is a blend of all eight. Thrust is bounded, per thruster and in total, and a controller that knows the bounds can plan around them instead of saturating. Thrust is late: 30 ms of delay plus an 80 ms spin-up lag is two control ticks before a command has mostly arrived. And the physics is well understood: the Fossen model of a rigid body in water predicts Talos's motion over a couple of seconds well enough to plan with.

It is a nonlinear MPC because it predicts with the full nonlinear Fossen model: quadratic drag, Coriolis and buoyancy that depends on attitude, plus the quaternion attitude itself. A linear MPC would fix one linearization (say, about a level hover) and plan with that forever, which is wrong as soon as Talos is moving fast, turning or tilted. riptide_mpc instead rolls the nonlinear model forward every tick and relinearizes along that predicted trajectory. It then takes one Gauss–Newton step of the nonlinear problem, a sequential quadratic programming (SQP) step in the real-time iteration scheme (Chapter 6). Each QP is linear-quadratic; the problem it is solving is not.

The price is computation and a model you have to identify. riptide_mpc pays the first with a careful formulation (a small dense QP, one Newton step of the nonlinear problem per tick) and the second with pool identification runs and an online disturbance estimate that soaks up what the model gets wrong.

About the browser version

The simulations on this site run a line-by-line JavaScript port of marine_dynamics, fossen_model, thruster_dynamics, motion_profile, path_plan, mpc and box_qp, with Talos's identified model and the controller settings from config/mpc.yaml. Two differences: the browser predicts with a 10 ms integration step instead of 2 ms so it keeps up on a phone (the trajectories agree to well under a millimetre), and the path planner port leaves out roll/pitch blending, spins and moving look targets. The simulated "pool" is the same Fossen model, so here the controller's model is exact unless a demo says otherwise.
